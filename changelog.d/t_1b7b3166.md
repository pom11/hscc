- **The address guard could not see an address written next to a word character, so
  a real host in a label or in unspaced CJK prose was committed silently.**
  `FORBIDDEN` wrapped its alternation in `\b ... \b`, which requires the address to
  be delimited on BOTH sides by non-word characters -- it assumed an address is always
  written the way prose writes one. Measured on py3.11.16 and py3.13.12 over a 26x26
  both-sides delimiter cross-product (676 cells), **315 cells missed**. The blind set
  collapses to a boolean: a word character immediately before OR after the address.
  Because `\w` is Unicode, that was not only identifier-style adjacency
  (`LABEL_<addr>`, `host<addr>`, `<addr>backup`) but **ordinary unspaced CJK prose**
  (`服务器<addr>`, `<addr>的配置`) -- the operator writes Chinese in docs and commit
  messages, so this class was live, not hypothetical. It was also the mechanism behind
  t_3e6d3db7's compiled-`.pyc` blind spot. Non-word delimiters were never affected:
  minified JSON, CSV columns, `key=<addr>&x=1` query strings and URLs all matched
  before and still do. The boundary is now an explicit anti-truncation guard,
  `(?<![0-9])(?:...)(?![0-9])`: what must be rejected is an address that is a FRAGMENT
  of a longer digit run (a version number, a truncated quad), which a letter is not.
  The miss set drops to exactly the digit row and column (51 cells), deliberately.
  `[0-9]` rather than `\d` because `\d` is Unicode-aware in text mode and ASCII-only
  in bytes mode, and `.github/scripts/redact_guard_report.py` ships this `.pattern`
  over a child-process protocol to be re-compiled on the far side -- the two forms
  must not be able to disagree. Detection can only have widened, never narrowed, and
  that is pinned as a property rather than asserted: the test rebuilds the old `\b`
  form **from the shipped pattern at runtime** and proves old is a subset of new, so
  the single-implementation pin stays the only place the pattern is written.
  `10.0.0.x`, `100.64.0.1` and the sanctioned `100.64.0.0/24` block are accepted
  exactly as before, including when they too abut a word character. Whole tracked
  tree re-scanned through `scan_blob`: **0 offenders**, so no developer's commit path
  gains a new false positive. Current real-world exposure was measured at **zero** --
  1101 tracked text files contain no forbidden-shaped address adjacent to a word
  character at all -- but the class is content-shaped, not file-shaped: one unspaced
  Chinese sentence naming a host puts the repo in it immediately, and the reproduced
  compiled-blob instance shows the mechanism is not hypothetical. Reasoning, the full
  matrix, limits and the mutation battery:
  `docs/audits/address-guard-boundary-t_1b7b3166.md`.
