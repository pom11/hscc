- **The premise "packed legs inherit SIGINT ignored" is false for the runner as
  it is written, and the serial and packed gates test the *same* signal posture
  today.** Measured end-to-end through the real `scripts/run_tests.sh` (a stand-in
  `HSCC_TEST_PY` that reports its own dispositions instead of running pytest — the
  runner's own launch line, nothing edited):
  `HSCC_TEST_PARALLEL` unset **and** `=2` both hand the leg
  `INT=default_int_handler QUIT=SIG_DFL TERM=SIG_DFL HUP=SIG_DFL`, i.e. born able
  to trap. The switch is `set -m` at `run_tests.sh:837`: bash 3.2 non-interactive
  with job control in effect does *not* apply the POSIX "asynchronous command
  ignores INT and QUIT" rule to its `&` children — measured in all four
  combinations (`neither` → INT/QUIT `SIG_IGN`, `m_only` → default, `trap_only` →
  `SIG_IGN`, `both` → default), so `set -m` is what severs it and the runner's own
  `trap on_sigint INT` contributes nothing to the child. The bad birth is real but
  comes from `cmd &` **without job control** — the audit rigs
  (`docs/audits/support/t_44a09412/pair_chase.sh:34,36`), not from the pack.
- **The `set -m` protection has a limit worth naming: it stops bash ADDING the
  ignore, it does not undo one already handed down.** A parent (the analogue of a
  daemon or a wrapper) that is itself ignoring INT, launching the same pack shape,
  yields `INT=SIG_IGN QUIT=SIG_IGN` legs **with and without** `set -m` (2 runs
  each): only `SIG_IGN` survives `execve`, so nothing between can repair it. That
  is why the fix for a trap-a-child case belongs on its own launcher (#833) and
  why the runner is only asked to be consistent with itself.
- **Which gate the queue runs:** the serial one. `merge_queue.RUN_TESTS_GATE` is
  `bash scripts/run_tests.sh` (merge_queue.py:264), the narrowed form only prepends
  `HSCC_TEST_LEGS` (:1235), and `HSCC_TEST_PARALLEL` appears nowhere in the tree
  outside `run_tests.sh` and its own tests — unset means the serial loop
  (`run_tests.sh:610`). GitHub CI runs one leg per job the same way
  (`.github/workflows/pytest-legs.yml:288-290`).
- **The daemon-as-spawner path is self-neutralising.** `merge_queue.py:2062` spawns
  the gate with plain `Popen(start_new_session=True)`, so the gate inherits the
  daemon's disposition — but only an *ignored* disposition survives `execve`, and
  the daemon entry installs INT/TERM/HUP handlers before it ever gates anything
  (pinned by `test_daemon_entry_signal_mask_t_81e00872.py`). Measured both halves:
  a parent born `SIG_IGN` that installs handlers → child `INT=default`; the same
  parent without handlers → child `INT=SIG_IGN`. So a queue gate cannot inherit the
  ignore through a daemon that handles its own stop signals.
- **Mechanism confirmed at test level rather than assumed**: an inherited `SIG_IGN`
  does reach a test's own `Popen` child through a real pytest session (pytest
  installs no SIGINT handler of its own, so there is nothing for `execve` to reset),
  and a `/bin/sh` (bash 3.2) born ignoring SIGINT does not run its INT trap — it
  survived the signal and had to be killed, where the same script born default
  caught it and exited 130.

  INT/TERM/HUP/QUIT — 4 `send_signal` sites, the rest `os.kill`) was run once with
  the suite born default and once with it born `SIGINT/SIGQUIT`-ignored, same
  interpreter, same env, same node ids. **One case changes verdict.**
