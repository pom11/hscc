### Fixed

- **A template may now declare at most one `proxy: true` family**
  (`hscc-cluster/cluster_template.py::_structural_validate`,
  `hscc-cluster/tests/test_one_proxy_per_cluster_t_6283c79f.py`).
  sparkrun keeps ONE gateway per cache dir — `GatewayState.__init__` binds
  `resolve_sparkrun_cache_dir()/"proxy"`, `is_running()` reads the PID from that
  one shared `state.yaml` (so it is port-agnostic), and `_start` answers every
  later start with `ProxyAlreadyRunning` → the CLI `sys.exit(1)`. So on a
  template with two proxy families, `apply`'s Step 4 got `loaded=False` for
  every family after the first while the `proxies/` step still reported
  `"status": "ok"`, and `_proxy_front_for_target` wrote
  `http://localhost:<refused port>/v1` into consumer configs. The rule is now a
  named structural error, so `hscc template validate` and `apply`'s pre-flight
  gate block before any write, stop or start. `sparkrun proxy start` has no
  `--cache-dir`/`--instance`, so this cannot be fixed by passing a per-family
  instance — that would need a sparkrun multi-gateway feature.
- **The 8 shipped templates that declared two proxy families were corrected**
  (`3node/balanced`, `3node/flux2-media`, `4node/balanced`,
  `4node/coding-plus-fast`, `4node/dual-orch`, `4node/quality`,
  `4node/review-heavy`, `8node/coding-plus-fast`): the extra family now says
  `proxy: false`. Which family keeps the proxy is not a choice — the resolver
  mints `proxy_port` in declaration order and only the first start can ever
  load, so the family that lost the key is exactly the one that never had a
  gateway; its consumers move from a dead proxy port to the primary node's
  direct endpoint. The single gateway auto-discovers every family's endpoints.

### Verified

- 8 new tests, fakes only: `subprocess.run` is replaced by a fake that models
  sparkrun's single-gateway state (one state file, refusal wording copied from
  `sparkrun/cli/_proxy.py`), so the suite's sparkrun fence stayed at **0
  live-CLI resolutions** and the live proxy was not touched. Red-before for the
  guard: with the check removed, the two-proxy apply proceeds into Step 4 and
  the blocked-apply tests fail.
