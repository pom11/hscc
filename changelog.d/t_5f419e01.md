- **`hscc doctor` can now see a stale sparkrun reservation in the gateway's OWN
  ledger — the row that actually blocked an orchestrator launch.** #843 shipped
  the row asking each cluster node about its own reservation ledger, and
  nothing else; its module docstring stated the premise outright — the two
  documented sparkrun calls are made "on the node". That premise is false for
  the incident it was written for: the stale row that blocked the orchestrator
  launch sat in the gateway host's own `~/.config/sparkrun/operations.sqlite3`
  (`process {"pid": 71357, "platform": "darwin"}`), because it is the sparkrun
  client `hscc apply` spawns LOCALLY that holds that claim — ledger and owner
  pid both local. **The node-only probe reported that host clean.** The row now
  probes both ledgers, through the SAME two calls (`reservations(root)`,
  `reconcile_reservation(root, owner, acknowledge_effects=True)`), the local one
  run under hscc's own sparkrun venv python — resolved by
  `hscc_daemon.sparkrun_bin`, the resolver hscc already uses for local sparkrun
  work, never a PATH `python3`.

  Liveness needs no new logic and must not get any: sparkrun answers `alive`
  with its own `process_identity` compare, and a compare is only valid on the
  host that owns the pid. That is why the local ledger cannot be read from a
  node either — a `platform: "darwin"` identity matched against a node's
  `/proc` identity is never equal, so a remote probe would call a LIVE local
  owner dead, and "dead" is the only thing that licenses a delete. So the
  corrected rule is *ask liveness where the owner process lives* — one
  question per ledger, never one question for the fleet.

  The boundaries that made #843 correct are unchanged, and now hold for both
  legs: hscc still never opens the ledger — zero `sqlite3`, zero `connect()`
  (pinned by an AST sweep of the module, not by a grep that a reworded comment
  could dodge). An answer we cannot trust is an ERROR, never "no
  reservations". Release stays explicit-operator-only and fail-closed: an
  unanswered probe — local or remote — is `NOT touched` and issues no
  reconcile, a live owner is `LEFT` with sparkrun's own refusal named, and
  both doors REFUSE to exist inside a pytest process, so a suite that forgets
  to inject can neither reach the fleet nor read the operator's own ledger.
  Classification of an answer and the release rule are each ONE function
  shared by both legs, so the local ledger cannot inherit a weaker rule than a
  node's.
