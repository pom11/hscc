* `hscc api stop` no longer orphans the live-gateway sidecar. `api_cli`'s
  SIGTERM/SIGINT handler answered with `os._exit(0)`, and `os._exit` does not
  run `finally:` blocks — so the `finally:` in `_serve` that owns the sidecar
  teardown (`gateway_bridge.shutdown()`, then `clear_api_state()`) never ran on
  the stop path. The supervised `hermes serve` survived, reparented, holding
  the API process's token: the same stale-token 403 the handler was written to
  prevent, reached from the other entry point, and produced by the ordinary
  stop verb whenever the unit is not launchd-managed. The stop is now
  cooperative — the shape `api_server.serve_main` got in #615: `_serve` honours
  a stop flag before serving and inside the join loop, so returning from
  `_serve` is the only way out of the serving process, and that one `finally:`
  stays the only door. The API now also writes one closing `HSCC API stopped`
  line to `~/.hscc/api.log` on both entry paths, so a stop that worked has a
  line to be checked against.
* The same stop had a second door, found by the leg run and closed in the same
  change: the handler did its own work inline, starting with
  `daemon_ops.log(...)`, and a signal handler runs on the thread it interrupts.
  `daemon_ops.log` holds `daemon_ops._handlers_lock` — a plain, non-reentrant
  `threading.Lock` — while it resolves the rotating handler, so a stop landing
  while the API was writing a log line (it writes several on the way up, which
  is exactly when `hscc api stop` arrives) left the handler waiting on a lock
  only its own thread could release. It never returned, never marked anything,
  and `_serve` never reached the teardown; `hscc api stop` escalated to SIGKILL,
  which skips the teardown too. The handler is now two operations and nothing
  else: set a lock-free stop flag (deliberately not a `threading.Event`, whose
  `set()`/`is_set()` take a lock the serving loop holds on every pass) and hand
  the log line, the PID-file bookkeeping and the shutdown request to a helper
  thread. Latent in the old handler as well — it logged before it hard-exited,
  so the same landing hung the process instead of orphaning the sidecar.
