- **`hscc autodown status` no longer misreports an unevaluable PR/CI
  interlock as "open PR / active CI run", and the unevaluable WARN is
  emitted once per unreachable spell, not once per daemon tick.**
  `_has_active_pr_ci` (hscc_daemon/autodown.py) called
  `_note_prci_unavailable(reason)` on the unreachable path and THEN
  `_note_prci_active()`, which rewrote the bookkeeping back to the
  healthy-active values (`ok=True`, `reason=""`, `warned=False`).
  Consequences: (1) `prci_check_state()` reported `ok=True`/empty reason
  and `prci_blocking_signal()` returned `"PR/CI"` instead of the
  `_PRCI_UNREACHABLE` sentinel, so `_cmd_status` rendered
  "open PR / active CI run on a tracked repo" (and the human panel
  `[warn]ACTIVE`) when the truth was "PR/CI source unreachable —
  treating as active (fail-safe)" / `[error]UNEVALUABLE` — the operator
  saw the WRONG reason for why teardown holds; (2) the `warned` flag
  reset on every call, so the daemon's 30s cycle re-emitted the WARN
  every tick while `gh` stayed unreachable, exactly what
  `_note_prci_unavailable`'s docstring promises against. Fix is
  bookkeeping-only — the fail-safe polarity is untouched (unreachable
  still ⇒ True/active ⇒ never tear down; the existing polarity tests
  pass unchanged): the two notes are now EXCLUSIVE (the active-note is
  an `else` branch), `_note_prci_unavailable` records
  `blocking=_PRCI_UNREACHABLE` itself — mirroring the kanban interlock's
  `_note_blocking(_UNREADABLE_BOARD)` — so the raising-checker path
  surfaces the sentinel too, and the positively-clear path now records
  the full resolution via `_note_prci_clear()` (was
  `_note_prci_blocking(None)`), so a recovered source cannot leave a
  stale unreachable `reason` behind a clear signal. `probe_prci_activity`
  verified untouched: it never writes `_PRCI_LOAD`. Pins:
  `test_autodown.py::TestHasActivePrCi` gains an autouse `_PRCI_LOAD`
  snapshot/restore fixture + six state/WARN pins (unevaluable state after
  unreachable and after a raising checker, WARN-exactly-once across five
  ticks, active/clear after unreachable report truthfully, recovery
  re-arms the WARN); `test_autodown_cli.py::TestStatus` gains
  `test_status_prci_unreachable_real_predicate_end_to_end`, which drives
  the REAL `_has_active_pr_ci`/`prci_check_state`/`prci_blocking_signal`
  (import-captured, the `_REAL_LIST_ACTIVE_CRON_JOBS` precedent) through
  the supported `_screen_prci` seam and asserts `--json` renders
  "unreachable" in `blocked_by` with `prci_ok` False. All four mutation
  probes (reintroduced clobber ×2, removed sentinel line, blocking-only
  clear path) turn the new tests red; suite green at this base.
