- **The watchdog and trigger-engine cadences were private `stop_event.wait()`
  numbers, invisible to `hscc verify` (GAP-B-6).** `run_daemon_loop` started
  both of its dedicated threads with `wait(30)` and `wait(15)` written inline,
  so neither cadence was a `PERIODIC_INTERVALS` key even though BOTH already
  publish a stream state file every tick (`watchdog.json` from
  `lifecycle.pipeline_watchdog`, `triggers.json` from `trigger.trigger_engine`).
  verify's per-stream staleness rule keys off `PERIODIC_INTERVALS`, so those two
  streams silently fell back to the flat `max_age_s` window: a caller that
  tightened the window (`hscc verify --max-age`) could cry wolf on a healthy
  daemon between ticks, and the SOT rule "cadence lives in PERIODIC_INTERVALS"
  was quietly false for two of the daemon's own loops. Both cadences are now
  `PERIODIC_INTERVALS` entries (`"watchdog": 30`, `"triggers": 15`) and the two
  loops read them from there; the thread-start log lines print the SOT value
  instead of a hardcoded `interval=30s` / `interval=15s`. Nothing the watchdog
  or the trigger engine DOES is unchanged in behaviour: same 30 s / 15 s ticks,
  same stamp writers, same error isolation.
