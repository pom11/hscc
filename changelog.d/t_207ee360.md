- **A template switch left a stale `serve_cmd` on the unit and every status
  read errored about it forever (t_207ee360).** apply's Step 1 intentionally
  carries recorded `serve_cmd` values across the serving.json rewrite — so
  across a template switch it carried the PREVIOUS recipe's command onto the
  unit's new fields too. The stored command then contradicted the unit it sat
  on, and the daemon's refuse-a-corrupt-record guard did its job: every
  `autodown status` / `fleet_up_plan` printed `serve_cmd refused ... using
  derived command` for that unit — permanently, on every read (live incident:
  the operator's `orch` unit, key removed by hand). The carry-forward is now
  NARROWED, not removed: a record is preserved only while its PLACEMENT
  (recipe path, `--hosts` node set, `--port`) still matches the unit's
  fields; a placement contradiction means stale by definition, and the record
  is dropped and named in the apply step
  (`serve_cmds_stale_dropped: ["orch: serve_cmd recipe ... != unit recipe ..."]`).
  Placement is judged through the `_serve_cmd_flags` normalisation — never raw
  argv equality — and uses the SAME definition the daemon guard applies
  before trusting a record: the carry decision and the refusal decision must
  agree, or apply re-plants what status reads then refuse. Flag-only
  differences are NOT dropped: a recorded flag the current render dropped is
  drift/override evidence, which is the half the carry exists to preserve and
  the next apply's drift check is its arbiter. Dropped records are never
  rewritten: provision stamps only what it actually launched, and the carry
  must not claim a launch that did not happen; a recipe-changed unit is
  relaunched by provision in the same apply and re-stamps a fresh command.
  The existing pin
  `test_apply.py::TestServeCmdCarriedAcrossRewrite` was deliberately narrowed
  to the placement-matching case, and the non-regression half (placement
  matches, flag differs -> survives byte-identical) is pinned by new tests.
