kind: Fixed
task: t_242506d7

* A crashed API now costs 1 on the `hscc api start` path as well as on the launchd
  one. `api_cli._serve`'s `except Exception` arm logged `HSCC API crashed: {exc}` at
  ERROR and then fell through to the same `finally:` a clean cooperative stop uses,
  so it returned `0 if stop_clean else 1` with `stop_clean` still True — the serving
  grandchild of `hscc api start` exited 0 having died. `serve_main` returns 1 for the
  identical failure (`except Exception as exc: print("hscc-api: crashed: ...",
  file=sys.stderr); return 1`), so the two entrypoints disagreed about what the same
  failure costs: the class of divergence t_54159e29 closed one path over, on the
  crash path instead of the abandoned-listener one. `_serve` now keeps a `crashed`
  flag beside `stop_clean` and returns 1 for either.
* `crashed` is a separate flag rather than `stop_clean = False`, for the reason
  `serve_main` keeps the two conditions separate too. `stop_clean` is what turns the
  abandoned-listener WARN on in the `finally:`, and a crash abandoned nothing — it
  never got as far as a stop. Reusing the one flag would have the API report a wedged
  listener loop it never had, and send someone to debug one. Measured: with that
  formulation the case reddens on the log reading `HSCC API: WARNING: listener loop
  within 5s did not stop — abandoned` after a crash that wedged nothing. Both
  conditions cost 1; only one of them says why.
* The teardown is untouched. A crash still falls through to the same `finally:` that
  owns the gateway sidecar shutdown (t_56552ecc) — the new flag is assigned in the
  `except` arm and read only in the return expression, and nothing that can raise
  went into the block. The three pre-bind `os._exit` calls (2 for a profile-root
  refusal, 1 for a bind or token failure) stay as they are: nothing bound, no
  sidecar, nothing to tear down.
* The exit code stays a report, not a trigger, exactly as for the abandoned-listener
  code: `hscc api stop` stops by signalling the pid file's instance and waiting for
  it to vanish, and the serving grandchild is reparented as soon as the intermediate
  fork exits, so nothing supervises on this status. What it buys is that "stopped",
  "stopped by giving up on a wedged loop" and "died" stop being the same number on
  both entry paths.

* `hscc_daemon/tests/test_api_cli_stop_sidecar.py` grows 3 cases (24 -> 27, 15.8 s):
  the `serve-crashed` arm, its `-` control, and one source pin. Hermetic as the rest
  of the file is — loopback and `::1` only, a throwaway HOME with a fixture token,
  and the fake `gateway_bridge` that writes a marker instead of supervising a real
  `hermes serve`.
* The crash is injected at the `serve_forever` seam and nothing else is stubbed: the
  real `create_servers` binds both listeners, the sidecar is really spawned, and the
  arm asserts its pid is dead afterwards — so the case proves the teardown still
  belongs to the `finally:` on a path that never receives a signal. Injecting there
  rather than deeper is deliberate and says so in the arm: nothing raises out of
  `_MultiServer.serve_forever` on purpose (its listener loops run on their own
  threads, where an exception dies in the thread, and its flag branch returns the
  hosts it abandoned), while what it can still do is fail on the way — a waiter
  thread that cannot start. That unplanned class is what the arm stands in for, and
  it is the same reason t_60932269 injected its wedge at `service_actions`.
* The pair is what stops "reports a crash" from being satisfied by a build that
  reports a crash always. The `-` control runs the same arm with the seam left alone
  and asserts rc 0, no crash line and no abandoned-listener WARN; the crash arm
  asserts rc 1 and the ERROR line naming the injected failure.
* Mutation-probed twice, and the two mutants are not caught by the same witness.
  `return 0 if stop_clean else 1` (the fix's own line reverted) reddens the case on
  `harness: _serve returned rc=0` AND the pin, on the arm writing `['crashed']` while
  the returned expression reads `['stop_clean']`. Adding `stop_clean = False` to the
  crash arm instead — a formulation that also exits 1 — reddens ONLY the case, on the
  WARN that should not be there. The pin cannot tell those two apart and was never
  meant to; it says the crash must reach the verdict, the pair says which verdict is
  honest.
* One observation about the arm, recorded not explained: with the pid file absent (as
  it is in the harness, which skips the double fork that writes it),
  `daemon_ops.log` echoes to stderr, so the child's own stdout carries the API's log
  lines. Production `hscc api start` writes that pid file before `_serve` runs, which
  is why the report is on the log file and not on a print (t_54159e29).
