# iOS operator console — v1 design

Status: approved in brainstorming 2026-08-28. Supersedes the ad-hoc app built
card-by-card through 2026-08-27.

## Why this exists

The app connects and compiles, but it cannot do the one job that matters:
hold a conversation with a project's orchestrator. The operator's verdict was
that it "cannot replace the current Telegram way of chatting in each project".
This design makes the app the primary chat surface and raises the rest to a
standard that can be sold to other HSCC operators.

## Decisions (locked)

1. **Telegram is replaced.** The app talks to Hermes directly, in each
   project's own session.
2. **Audience: other HSCC operators.** Strangers install it against their own
   cluster. Onboarding, multi-cluster and legible errors are requirements, not
   polish.
3. **Chat shows live activity** — streaming tokens plus visible tool calls.
4. **hscc-api bridges to the Hermes gateway.** One endpoint, one bearer token.
5. **No push notifications.** Jobs run server-side; the reply waits in the app.
6. **Project-first IA** — project list, then Overview / Chat / Board / Settings.
7. **Every existing surface is kept and fixed** — but Siri, the widget and the
   Live Activity go LAST, as they have never executed once.

## 1. Chat architecture

Today `hscc-api` shells `hermes chat -Q --continue <session>` and scrapes
stdout. It cannot stream, cannot show tool activity, cannot create a session,
and reports every failure as one misleading string.

    iOS  --WSS/tailnet-->  hscc-api  --WS/loopback-->  hermes serve  -->  <project> session
         (one bearer token)          (holds gateway credential)

`hermes serve` is Hermes' JSON-RPC/WebSocket gateway (default :9119),
documented as the interface for "the desktop app and remote clients".

Consequences:
- the app joins the SAME session with the full agent loop — tools, kanban,
  memory — not a parallel one-shot channel
- streaming and tool events arrive as gateway events, not scraped text
- Hermes stays on loopback; only hscc-api is exposed on the tailnet
- jobs live server-side, so backgrounding the app cannot lose a reply

Two defects fixed here:
- **session bootstrap** — `--continue` resumes but never creates, so a fresh
  project can never be chatted with. The bridge creates on first message.
- **error attribution** — `if proc.returncode != 0` currently reports
  "session not ready (create it first)" for EVERY failure, discarding real
  stderr. This sent the operator (and the author of this design) chasing a
  missing session that existed. Failures must name themselves: model
  unreachable, session missing, timeout after N seconds.

**Unproven dependency.** `hermes serve` exists and is documented, but its event
schema and auth handshake have NOT been verified. If it cannot emit tool
events, the streaming promise degrades to text-only. A spike proves this
BEFORE anything is built on it.

## 2. Information architecture

Root: a project list. Inside a project: Overview / Chat / Board / Settings.
Cluster (nodes, GPU, wedges, autodown, templates) is a separate root surface —
it is about the fleet, not any one project.

- **Project row** — name, one health glyph, and the single fact that decides
  whether you tap: reply waiting, cards needing review, or last activity.
- **Overview** — answers "what is the state of this project?" in ~3 seconds:
  running/ready/blocked counts (blocked most prominent), repo branch and
  ahead/behind/dirty, session health and compaction headroom, and a tappable
  last-reply preview. The current top section renders wrong and is undiagnosed.
- **Chat** — full session history (not just this launch), streaming replies,
  collapsible inline tool activity, resend on failure, composer state that
  survives backgrounding.
- **Board** — the project's kanban: filter, open a card, read comments,
  recover a blocked one. Mutations stay confirm-gated.
- **Settings (project)** — resolved profile/session/board, model override.
  Connection and pairing move up to app-level settings.

**Shared foundation.** Each view was built by a different card in isolation,
which is why the app reads as assembled rather than designed. One theme applied
consistently, one loading/empty/error component set, one row style, one spacing
scale — enforced across every surface including the peripheral ones.

## 3. Sellable to other operators

- **First run** — QR pairing is the primary path, manual entry the fallback.
  A failed scan says why: wrong version, unreachable host, rejected token.
- **Multiple clusters** — host/port/token become a list of saved clusters with
  a name, health dot and last-connected. Also makes the app demoable.
- **Errors name the cause and the fix.** Never "Set a host, port, and token
  first" when all three are set.
- **Distribution** — TestFlight first; App Store is a later decision.
  Sideloading via Xcode does not scale past one person.
- **Security** — the QR carries a live credential: warn at pairing, support
  token rotation from the CLI, and state plainly in the docs that the tailnet
  is the security boundary.

## 4. Verification

Four bugs reached the operator on 2026-08-28 that local checks were
structurally incapable of catching:

| Bug | Why it was missed |
|---|---|
| `SetupQRCode` not in scope | compiled `find`-all, not the project's file list |
| `SettingsStore` self-before-init | `-typecheck` cannot see SIL diagnostics |
| Siri two-parameter phrase | Xcode's App Intents metadata processor only |
| Keychain token never saved | pure runtime |

`check_sources.sh` and `build_check.sh` now cover the first two. The operator
has declined installing the iOS simulator runtime, so **runtime verification is
not possible on the build host** — the App Intents and runtime classes have no
automated gate at all, and the operator's device is the only one.

Given that, the automatable win carries more weight:

- **Contract tests** exercising EVERY route the app calls with the app's exact
  payloads. Tonight's chat failure was a route/flag mismatch — the real route
  409s without `confirm` — which this class of test catches in CI rather than
  on a phone.
- **Device smoke checklist** for what cannot be automated: pair by QR, send a
  message, background mid-reply, scan with a wrong token.
- **Honesty rule** — anything unexecuted is labelled unexecuted, in cards and
  in release notes. No "verified" for something that has only compiled.

## Build order

1. Spike: prove the `hermes serve` event schema and auth
2. Chat pipeline (bridge, streaming, session bootstrap, error attribution)
3. Projects list + Overview + shared design foundation
4. Onboarding, multi-cluster, error legibility
5. Verification harness (contract tests, smoke checklist)
6. Siri, widget, Live Activity — last, never yet executed

## Out of scope for v1

Push notifications. App Store submission. Any backend other than HSCC.
