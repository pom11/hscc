# Audit note — t_d5780187: make tests/test_standup.py hermetic (stop live-state flake)

## Problem

`hscc-project/tests/test_standup.py` was LIVE-STATE FLAKY: results flipped
based on the operator's real Hermes runtime and board state, not on the repo
code. Measured 2026-09-24: the RC2 worker reported "30 pre-existing
test_standup failures (Hermes kanban_db sqlite3.OperationalError)"; an
independent clean run gave 59 passed / 0 failed — same code, no change.

THIS run reproduced it precisely. With `HERMES_DELEGATED_CHILD_CONTEXT=1`
(the read-fence `run_tests.sh` unsets for exactly this reason; it is set in a
dispatched worker session), `test_standup.py` failed 26 tests with a cascade
of `sqlite3.OperationalError: unable to open database file` from Hermes'
`kanban_db_connect.connect()` (opens `?mode=ro` and refuses to create the
board on a descendant's behalf). Unset the fence → 59/59.

## Which lines read live state, and how they were made hermetic

Two distinct leaks, both through `flightdeck/core/kanban.py` resolving the
Hermes library via `kanban._load_kanban_db()`:

1. **The freshness-watermark read (the broad cascade).**
   `standup.gather_data()` calls `kanban.list_board_watermarks(boards=...)`,
   which falls through to `_load_kanban_db()` → real Hermes → real
   `connect(board=...)`. Only 5 of ~59 tests monkeypatched
   `list_board_watermarks`; every other test that drove `gather_data` opened
   the operator's ACTUAL board for a watermark it never even asserted on.
   Under the read-fence that open died with `OperationalError` (26 tests);
   on a non-empty board it would silently change rendered "data as of"
   lines. Fixed with an **autouse fixture** `_hermetic_watermarks` that stubs
   `kanban.list_board_watermarks` → `{}` (exactly what an EMPTY host reads),
   overridable by the tests that DO assert on freshness.

2. **The settled-card regression test**
   (`test_standup_never_reports_settled_cards_as_running`, formerly
   `tests/test_standup.py:1440-1454`). It inserted `~/.hermes/hermes-agent`
   on `sys.path`, imported the REAL `hermes_cli.kanban_db`, and routed
   `_load_kanban_db` at it — so it depended on a live Hermes install AND,
   through `HERMES_KANBAN_HOME`, still hit the read-fence `connect` when it
   tried to `create_task`/`complete_task`. Replaced with a faithful minimal
   in-memory `_FakeKanbanDB` (matching the Fake*DB pattern used elsewhere in
   the flightdeck tests) injected via `_load_kanban_db`, so the REAL
   `list_cards` code — including the `SETTLED_STATUSES` filter that is the
   regression under test — runs against isolated in-memory state. The
   `~/.hermes/hermes-agent` sys.path import, `HERMES_KANBAN_HOME` setenv, and
   `pytest.importorskip`/skip guard are all removed; nothing touches the
   operator's disk or Hermes runtime. `import os`/`import sys` (only used
   there) were dropped.

## Regression value preserved

A throwaway teeth-check confirmed the fake + real `list_cards` genuinely
exercises the filter: a `done` card created through the fake is excluded by
the real `SETTLED_STATUSES` filter, while a `running` card from the same fake
is included (the exclusion is the filter, not the fake silently dropping
cards).

## Suite numbers

isolated board hermetic via the fake; `HERMES_KANBAN_HOME` and the live
`~/.hermes/hermes-agent` import are gone. A clean checkout now passes on any
host under either interpreter, with or without a Hermes install, and regardless
of the delegated-read fence.
