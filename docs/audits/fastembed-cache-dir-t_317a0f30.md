# One fastembed model cache per host (t_317a0f30)

Status: implemented on branch `wt/t_317a0f30`. Card: *Set FASTEMBED_CACHE_DIR at
spawn time: 7x87 MB model caches, one per cwd an agent has run in.*

Nine directories, **88,984 KB each — 782.1 MB total** (`du -sk` over the list
above), one model. Every one of them holds the same tree:
`models--Qdrant--all-MiniLM-L6-v2-onnx/{blobs,refs,snapshots}`, and the largest
blob hashes identically (`sha256 bbd7b466…`) in the four trees compared — the two
under `~`, the one in `hscc`, and one freshly downloaded by this card's probe. So
"nine copies of one model" is measured, not inferred from equal sizes.

Two of them are not agent workspaces at all — the `hscc` repo root (a pytest
leg runs with the repo root as cwd) and `~/.hermes/hermes-agent` (the gateway's
`WorkingDirectory`, see below). That is the tell: the cache follows the *cwd*,
not the repo, not the profile, not the agent.

## Root cause, confirmed at the binary

`memori` 3.3.6 vendors the Rust `fastembed` crate inside
`site-packages/memori_python.abi3.so`. `strings` on the shipped `.so` shows both
sides of it:

```
.fastembed_cachemodel_max_length=     ← the default, a RELATIVE path
.../fastembed-5.13.1/src/common.rs
HF_HOME  HF_ENDPOINT  https://huggingface.co  FASTEMBED_CACHE_DIR
```

The default is the relative literal `.fastembed_cache`, so it resolves against
whatever cwd the process happens to be standing in; `FASTEMBED_CACHE_DIR` is the
override the crate reads. `memori/_config.py:62` (`self.model =
"all-MiniLM-L6-v2"`) names exactly the repo in every cache, and
`memori.embed_texts` → `memori._rust_core.embed_texts_native` is the call that
constructs the model. No Python `fastembed` package is installed anywhere on
this host — the writer is inside the `.so`, so no Python-level `fastembed`
configuration can reach it. The only lever is the environment variable, and it
has to be in the environment **of the process that loads the model**.

## Why the plugin sets it, and not a launcher

The card asked for the variable to be set "in the environment Hermes uses to
spawn agents and test runs (and any gateway/worker launcher path)". Investigat-
ing that path first, because it is where the ask pointed:

* **The gateway's launchd plist is not ours.** `~/Library/LaunchAgents/
  ai.hermes.gateway.plist` does carry an `EnvironmentVariables` dict (that is
  where `HSCC_MEMORI_AUGMENT_URL` / `_MODEL` in every worker env come from), but
  the plist is written and regenerated by hermes' own installer
  (`hermes_cli/gateway_launchd_runtime.py`). Hand-editing it is an edit to
  infra another project owns, and it is overwritten by the next
  `hermes gateway install`. Per the fleet rule — *hermes owns the agents* —
  that is not a place to put our cure.
* **The dispatcher copies its own environment.**
  `hermes_cli/kanban_db_dispatch.py:2884` spawns each worker with `env=env`,
  where `env` is a scrubbed copy of the dispatcher's `os.environ` (it strips the
  delegated-child marker, pins the board paths, pins the hermes tree). So a
  worker inherits whatever the *gateway process* had. That means a plist edit
  would work for dispatched workers — and for nothing else: not a `hermes chat
  -q` typed in a shell, not cron, not the TUI or desktop app, not a pytest leg.
* **Every one of those processes imports the memory provider.** That is the one
  thing they have in common, and it is exactly the moment the variable must be
  set — before `memori` constructs the embedding model.

So the variable is pinned at **provider import**: `memori_byodb/__init__.py`
calls `ensure_shared_cache_env()` before anything can reach the SDK, and the
same module is wired into the cloud `memori` provider for symmetry. Whichever
way a process was started — launchd, dispatcher, cron, TUI, shell, pytest — it
loads the provider before it embeds anything, and the environment is correct by
then. That is the guarantee we actually control; a launcher-side pin is a
promise about one launcher.

`scripts/run_tests.sh` gets the same export independently (the way
`HERMES_DISABLE_LAZY_INSTALLS` and `HSCC_SKIP_COMPACT_PROBE` are exported
there): legs must not depend on a plugin being imported to keep 87 MB out of the
repo root, and a leg can reach the SDK without the provider.

## The three rules the helper implements

Pinned by `memori_byodb/tests/test_cache_env.py`:

1. **An explicit `FASTEMBED_CACHE_DIR` always wins.** Operator setting beats
   our default, including when it points at a path we would not have chosen.
2. **The default is `~/.cache/fastembed`** — deliberately *host-global*. Not
   `$HERMES_HOME`: profiles must share one cache, that is the whole point
   (`Path.home()` is unaffected by `hermes -p` rewriting `HERMES_HOME`). It
   follows the host's existing cache convention (`~/.cache/sparkrun`,
   `~/.cache/huggingface`, `~/.cache/hscc`).
3. **It fails open.** If the directory cannot be created — read-only home, no
   `HOME` at all — the environment is left exactly as it was and a `WARN` is
   logged, so memori falls back to its own default rather than to a path we know
   is unwritable. A cache optimisation must never be able to break the memory
   provider; that is also why nothing here raises.

Concurrency: a cold cache can now be populated by several agents at once. The
`.so` ships `fs2` advisory locking and the cache trees already contain the
`blobs/*.lock` files it takes, so parallel cold starts contend on a lock rather
than corrupt each other. Nothing in this change makes the first download
concurrent that was not already concurrent across two agents in two workspaces.

## Verification actually run

`scripts/verify_fastembed_cache_dir.py` is the acceptance probe the card asked
for: it runs from a scratch cwd, loads the real embedding model through the real
SDK, and asserts **where the bytes land** — because exporting a name the library
ignores would pass any env-var check. Three child processes, each with its own
scratch cwd and its own `$HOME`, each making a real `memori.embed_texts` call
that returned a 384-dim vector:

| case | what pinned the cache | landed in the pinned dir | cwd gained `.fastembed_cache` |
|---|---|---|---|
| `red` | nothing | — (target never written) | **yes** — 16 files, 182,204,112 B |
| `green` | `FASTEMBED_CACHE_DIR` → a fresh, **non-existent** dir | **yes** — 16 files, 182,204,112 B | no |
| `plugin` | unset in the env; `import memori_byodb` set it | **yes** — under `$HOME/.cache/fastembed` | no |

Three things that make the `green` row worth more than a printed env var: the
directory named did **not** exist beforehand, so the library created it; the tree
that appeared is byte-identical in content to the nine on disk (`du -sk` 88,984 KB,
same blob hash); and `red` runs the same program with nothing pinned, so if the
override were ignored on this platform the two rows would look identical — they do
not. Each probe run also prints the pre-existing root count before and after
(`9 before, 9 after`) so a probe that added a tenth root would report itself.

`memori/_cache_env.py`'s twin, `memori_byodb/tests/test_cache_env.py` (23 tests)
and `scripts/tests/test_run_tests_fastembed_cache.py` (6 tests) cover the same
contract offline, so a regression names itself without needing the network: env
semantics including both fail-open branches, the import-time wiring in a child
process with a tmp `$HOME`, the call-site ordering as text, the runner export
extracted from `run_tests.sh` and executed under bash, and the two provider copies
not drifting.

## Deliberately NOT done

* **The nine existing caches were not deleted.** The card says so, and they are
  caches: reclaiming ~780 MB is a one-line operator decision, best taken on
  purpose rather than as a side effect of a code change. Once this lands they
  are all unreachable — nothing writes to them again — and this is the command:

  ```bash
  find ~ -maxdepth 8 -name .fastembed_cache -type d \
      ! -path "$HOME/.cache/fastembed/*" -print -exec rm -rf {} +
  ```

  (`~/.fastembed_cache` is included: it is a cache of the same model under an
  older default, and the new shared dir supersedes it. Deleting it costs one
  87 MB download on the next cold start if `~/.cache/fastembed` is not yet
  seeded — seeding it by hand is free: `mv ~/.fastembed_cache ~/.cache/fastembed`.)
* **No edit to the hermes-owned gateway plist**, for the ownership reason above.
  If the operator wants belt-and-braces at the launcher as well, the edit is one
  line in that plist's `EnvironmentVariables` plus
  `launchctl kickstart -k gui/$(id -u)/ai.hermes.gateway` — and it should be
  expected to disappear at the next gateway reinstall, which is precisely why
  the durable fix is in the provider.
* **The per-repo `.gitignore` rule from t_ae3e5f9b is kept**, not replaced by
  this. It is a commit guard for trees that run without HSCC's provider; this is
  the cure. They are not alternatives.
